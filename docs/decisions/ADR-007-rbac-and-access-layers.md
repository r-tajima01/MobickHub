# ADR-007: ロール設計と3アクセス層

## 決定日
2026-05-16

## ステータス
Accepted

## 文脈 (背景・課題)

MobickHub は当初「MC社員のみが見るアプリ」として設計されていたが、業務領域棚卸し (ADR-006) の結果、3つの異なるアクセス特性を持つ画面群が共存することが確定した:

1. **社内向け一般** — 営業所長・営業担当・配信担当・経理担当が日常使う画面 (営業 KPI、リース、中古車、活動入力など)
2. **経営機密** — 経理深掘り (`acc`)・KGI集約 (`bi`)・将来の戦略指標 (M&A検討・グループ会社横串) を含む。**役員報酬や人件費明細など、社内でも閲覧範囲を絞る必要のあるデータ**
3. **外部 (取引先ディーラー)** — PartnerConnect で開示する取引先向け画面。**他のディーラーの数字が絶対に見えてはいけない**

これらを単一の `/` 配下で扱うと:
- ロールチェック漏れによる情報漏洩リスク
- 外部ユーザーが内部画面に到達する事故
- 役員データへのアクセスログ取得 (`docs/project-context.md` L262 で要求) が困難

加えて、9期方針説明会スライド B-10 に示された通り、ディーラーは13カテゴリ・554店舗存在し、それぞれが互いに競合関係にある。データ分離は厳格に必要。

## 検討した選択肢

### 案A: 単一URLツリー + ロールごとの表示制御
- すべて `/` 配下で、コンポーネント側でロールチェックして出し分け
- **メリット**: URL構造がシンプル
- **デメリット**:
  - 経営機密と社内一般が同居するため、誤って `executive` 限定画面が露出するリスク
  - 外部ユーザーが内部画面のURLを直叩きする事故への防御が弱い
  - アクセスログを「経営機密への閲覧」単独で取りづらい

### 案B: 経営機密と外部を物理的に分離 (採用)
- 3つのアクセス層を URL接頭辞で分離:
  - `/` 配下 = 内部一般
  - `/exec/*` 配下 = 経営機密
  - `/portal/*` 配下 = 外部
- 各層に独立した layout.tsx + middleware.ts でアクセス制御
- **メリット**:
  - 物理分離による事故防止
  - アクセスログがパス単位で取れる
  - 将来の拡張 (`/portal/lessor/*`, `/exec/strategy/*` 等) に強い
- **デメリット**:
  - 共通コンポーネントを3層に提供する設計が必要
  - URL構造を最初に決める負担

### 案C: サブドメインで分離
- `mobickhub.mobilix-hd.com` (内部) / `exec.mobilix-hd.com` (経営) / `partners.mobilix-hd.com` (外部)
- **メリット**: 最も厳格な分離
- **デメリット**:
  - Vercel デプロイ・SSL証明書の管理が3倍
  - Phase 2 で外部だけ別ドメインにする方針は既に決定済み (`docs/project-context.md` L171)
  - 経営機密まで別サブドメインにするのは過剰

## 決定

**案B を採用。** ただし外部 (`/portal/*`) は将来 `partners.mobilix-hd.com` への分離を視野に入れる (既存方針通り)。

### アクセス層

| 層 | URL接頭辞 | 想定ユーザー | 制御 |
|---|---|---|---|
| 内部一般 | `/` `/daily` `/sales/*` `/fleet/*` `/used-cars/*` `/reports/*` `/quality/*` `/calls/*` `/e-rental/*` `/training/*` `/import` | MC社員 (executive 含む) | Supabase Auth + ロールベースRLS |
| 経営機密 | `/exec/*` (`/exec/bi`, `/exec/accounting/*`, `/exec/strategy/*`) | executive のみ | 上記 + middleware で `executive` チェック + アクセスログ |
| 外部 | `/portal/dealer/*` (将来 `/portal/lessor/*` `/portal/customer/*`) | dealer (外部ユーザー) | 別認証セッション + テナント分離RLS |

### ロール定義

| ロール | 範囲 | アクセス可能パス |
|---|---|---|
| `executive` | 経営者 (副社長・社長) | 全て (内部 + `/exec/*`) |
| `office_manager` | 営業所長 (4名) | 内部のうち自営業所範囲 + 全社サマリ閲覧 |
| `sales_rep` | 営業担当 (18名) | 内部のうち自分の活動 + 営業所内データ |
| `delivery_admin` | 配信担当 | `sf` 全営業所閲覧 + `/import` |
| `accounting` | 経理担当 | `acc` のうち経営機密外 (請求関連) + `/exec/accounting/*` の限定範囲 |
| `system_admin` | sys02 / 管理部 | 全領域 + `/admin/*` |
| `dealer` | 外部 (取引先) | `/portal/dealer/*` の自社分のみ |

### 実装方針

#### Supabase Auth + JWT カスタムクレーム
- ユーザー作成時に `app_metadata.role` でロールを設定
- ロールは JWT に含まれ、クライアント/サーバー双方から取得可能
- RLS ポリシーで `auth.jwt() ->> 'role'` を参照

#### Next.js middleware (`src/middleware.ts`)
- `/exec/*` への到達時は JWT の `role` が `executive` であることを必須化
- 違反時は `/` にリダイレクト + アクセスログ
- `/portal/*` は別認証セッション (内部ユーザーが間違えて到達しないようガード)

#### RLS ポリシー
- すべてのテーブルでロール + 所属 (営業所・取引先) を見て行を絞る
- `acc_*` の機密テーブル (役員報酬など) は `executive` のみ閲覧可
- `dp_*` の取引先データはディーラー側ユーザーには自社分のみ

#### アクセスログ
- `core_access_logs` テーブルで `/exec/*` 配下への閲覧を記録
- 記録項目: user_id, path, accessed_at, ip_address
- 監査要件: 役員データへの誰がいつアクセスしたか追跡可能

## 理由

1. **物理分離による事故防止**: 経営機密と外部データは「コードの注意深さ」ではなく「URL構造と middleware」で守る。コードレビュー漏れがあっても、別パスにいる限り到達できない。
2. **アクセスログの取得しやすさ**: パス単位で「経営機密にアクセスした」を区別できる。
3. **将来拡張への備え**: `/exec/strategy/*` (戦略指標) や `/portal/lessor/*` (リース会社向け) を追加するときに既存設計で吸収できる。
4. **9期スライド B-10 のチャネル別事業構造との整合**: 損保 / 販売店 / HC埼玉中 / 個人 と顧客セグメントが分かれている。`dealer` ロールはこのうち「販売店」チャネルの個別ディーラーに対応し、自社分のみ見えるテナント設計が業務実態と一致する。

## 影響

### ポジティブ
- 経営機密データの閲覧履歴が明確に追跡できる
- 外部ユーザーが内部画面に到達する事故を構造的に防げる
- 新規モジュール追加時の「どの層に置くか」判断がシンプルになる
- Phase 2 で `/portal/*` が独立サブドメイン化する際、コードの分離が既に済んでいる

### ネガティブ / 受容するリスク
- 共通コンポーネント (`<KPICard>`, `<DataTable>` 等) を3層から呼べる設計が必要 → `core` モジュールで集約
- ロール定義が変わったときの影響範囲が大きい (RLS・middleware・JWT すべて要更新)
  → ロール追加はマイグレーション + ADR で都度記録する運用にする
- `accounting` ロールが `/exec/accounting/*` の **どこまで** 見えるかが未確定
  → ADR-008 で経理データの機密度区分とセットで詰める

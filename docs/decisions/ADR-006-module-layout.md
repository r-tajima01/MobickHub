# ADR-006: モジュール構成と Phase 配分

## 決定日
2026-05-16

## ステータス
Accepted

## 文脈 (背景・課題)

CLAUDE.md 初版および `docs/project-context.md` 策定時点では、Phase 1〜4 の大枠 (営業ダッシュボード / PartnerConnect / 営業日報 / AIロープレ) のみ確定していた。一方、9期方針説明会スライド (本編 25枚 + 専門部会 18枚) を読み込んだ結果、以下が明確になった:

1. **9期方針の6つの柱** (損保 / 新規開拓 / 既存深耕 / 中古車 / 車両品質 / 応対品質) はそれぞれ独立した業務領域として KPI・SOP が定義されている
2. **リース・車両管理** (`flt`) は CLAUDE.md 未記載だが、MC のビジネスモデル (品質維持 → 中古車高値売却 → 新車再投資の好循環) の中核を担う
3. **中古車オークション** (`uc`) は KGI 「中古車粗利 3.56億」直結の成長事業で、USS出品の SOP が固まっている
4. **車両品質 / 応対品質 / eレンタカー** は「現場のチェックシート + 集計ダッシュボード」型の典型的な Excel置き換え案件
5. **経理分析** (`acc`) を sys02 が早期に立ち上げたいと表明
6. **経営機密エリア** が必要 (経理深掘り・役員専用 KGI)
7. **PartnerConnect** はディーラー向け外部ポータルとして社内画面と物理的に分離する必要がある

結果、Phase 1〜4 の中身を当初想定より細かく定義する必要が出てきた。特に Phase 2 のスコープと、`acc` の着手タイミングが論点。

## 検討した選択肢

### 案A: モジュールを1つずつ Phase 順送り
- 1 Phase = 1 モジュールに絞り、確実に届ける
- 例: Phase 2 = PartnerConnect 単独、Phase 3 = 営業日報単独、Phase 4 = リース…
- **メリット**: スコープが小さく、リリースリスクが低い
- **デメリット**:
  - レンタカーシステム連携が Phase 2 で走るのに、その派生モジュール (`flt`/`uc`/`dp`) がバラバラに着手される → データ基盤を作り直す
  - 副社長へのKGI接続が Phase 4 まで遅れる (中古車粗利・営業利益が出てこない)
  - sys02 が並走したい `acc` の居場所がない

### 案B: Phase 2 に `dp` + `flt` + `uc` + `bi` を同居
- レンタカーシステム連携を起点とした関連モジュールをまとめて立ち上げる
- 経営サマリ `bi` も同時に立ち上げ KGI を集約する
- **メリット**:
  - データ基盤 (レンタカーシステム連携) が1度で済む
  - 副社長視点で KGI 4指標が Phase 2 終了時に揃う
  - 「中古車収益拡大」が KGI 直結なので副社長承認を取りやすい
- **デメリット**:
  - Phase 2 のスコープが当初の倍近くに膨らむ
  - お盆前 8/8 リリース (PartnerConnect 副社長コミット) を守るには内部 Phase 分割が必要

### 案C: 中古車 (`uc`) のみ Phase 1 と並列で先行
- KGI 直結を優先し、中古車だけを先に立ち上げる
- **メリット**: 経営インパクトが早期に出る
- **デメリット**:
  - `flt` (リース管理) のデータがないと残存簿価・粗利計算が回らない
  - `uc` 単独だと「出品結果記録」程度の薄い機能になる

### 案D (採用): 案B + `acc` を Phase 1B として並走先行
- Phase 1 (`sf` 営業) と並行で sys02 が `acc` (経理分析) を裏で進める
- 5月末リリース後にお披露目
- 段階的アプローチ:
  - **Step 1**: 勘定奉行データ単独で `acc` を立ち上げ (Phase 1B)
  - **Step 2**: Phase 2 で `flt`/`uc`/`dp` を構築し、`bi` で経理×営業×車両のクロス分析を実現
- **メリット**:
  - 副社長公式コミット (Phase 1) は触らない
  - sys02 の「経理データを起点に活用したい」要望に応える
  - Phase 2 が始まる頃には経理ベースの経営状態が見える土台ができている
  - Phase 2 で `bi` がクロス分析を載せる時、`acc` 側のデータがすでにある
- **デメリット**:
  - sys02 の作業負荷が増える (Phase 1 仕上げと `acc` 立ち上げの並行)
  - 勘定奉行データ取り込み・経理側ヒアリングが新規リスク

## 決定

**案D を採用。**

### 確定 Phase × モジュール マトリクス

| Phase | 含むモジュール |
|---|---|
| 1 (実装中) | `sf` 営業 + `core` 基盤 |
| **1B (並走)** | **`acc` 経理分析 Step 1 (勘定奉行データ単独)** |
| 2 | `dp` PartnerConnect + `flt` リース + `uc` 中古車 + `bi` 経営サマリ (`acc` Step 2: クロス分析) + `core` 拡張 (RBAC + 外部テナント) |
| 3 | `act` 営業日報 + `vq` 車両品質 + `cq` 応対品質 + `er` eレンタカー |
| 4 | `tr` AIロープレ + MC全般 (`hr`/`crm` 等の選択着手) |
| 5+ | `rnt` レンタカー基幹置き換え (構想) |

## 理由

1. **データ基盤の連続性**: Phase 2 でレンタカーシステム連携を行う際、`flt`/`uc`/`dp` が同じデータ源を使う。バラバラに着手するとETLを作り直すコストが発生する。
2. **KGI接続の早期実現**: 副社長 KGI (売上 / レンタカー粗利 / 中古車粗利 / 営業利益) を Phase 2 終了時に全て集約できる。これは副社長への中間報告のインパクトを最大化する。
3. **経理データ起点の段階的アプローチ**: 勘定奉行から取得できる粒度のデータ (月次P/L・部門別損益) はそれ単独で経営分析として成立する。Phase 1B で立ち上げ、Phase 2 で MobickHub 内の業務データと組み合わせれば、横断的な経営ダッシュボードに進化できる。
4. **9期方針との整合**: 6つの柱のうち柱④ (中古車収益) は Phase 2 で `uc` として実装、柱⑤⑥ (品質) は Phase 3 で `vq`/`cq` として実装、柱①②③ は Phase 1〜2 の `sf`/`act`/`dp` でカバー、と全ての柱が Phase に紐づく。
5. **副社長公式コミットを動かさない**: Phase 1 (5月末リリース) と Phase 2 PartnerConnect (お盆前リリース) は副社長への約束。Phase 1B と Phase 2 の他モジュールはこの公式約束の外側で動かせる柔軟性を持つ。

## 影響

### ポジティブ
- 副社長への中間報告で「KGI 4指標すべて見える」を実現できる
- 「経理データを業務データと組み合わせる」という sys02 の方針が実現する
- 9期方針の6つの柱が全て MobickHub 上で可視化される
- 将来モジュール (`hr`/`crm` 等) を追加するときの判断基準が明確になる

### ネガティブ / 受容するリスク
- Phase 2 の工数は当初想定 (PartnerConnect 単独) より大きい
  → 内部的に **Phase 2A (PartnerConnect: 8/8 リリース)** と **Phase 2B (flt/uc/bi: 9〜10月)** に分割して進める
- 勘定奉行データ取り込みの新規ヒアリングが Phase 1 と並走で sys02 に負荷
  → 5月中に経理担当へのアプローチを開始 (詳細は ADR-008)
- レンタカーシステム担当者ヒアリングが Phase 2 のクリティカルパス
  → 5月中に副社長経由で正式依頼を進める

### 副社長への説明ポイント
- Phase 2 のスコープを当初想定より広げる ことの合意取得
- 「同じデータ源を使うので追加コストは小さい」「KGI が Phase 2 で全部見える」を強調
- お盆前リリースは PartnerConnect 単体で守る (Phase 2A)
- リース・中古車・経営BIは 9〜10月 (Phase 2B) で追加

# MobickHub — プロジェクト方針

> モビリティアンドコミュニケーション株式会社(MC)向け統合業務プラットフォーム
> ディーラー戦略支援を起点に、MC全社DXを段階的に実現する

---

## 1. プロジェクト概要(WHY)

### プロダクト名
**MobickHub** (モビックハブ)

### プロダクト位置づけ
モビック社の業務基盤として中核を担う統合プラットフォーム。営業支援を起点に、社内業務全般を取り込み、最終的にはレンタカー基幹システムの後継となることを視野に入れる。

### スライド上のプロダクト名(Phase 2)
**PartnerConnect FOR DEALERS** — MobickHub内のディーラー向け機能名として位置づけ。MobickHubが基盤、PartnerConnectが最初の機能、という階層構造。

### 業務目的
1. **9期方針「訪問の質を上げる『話題の壁』への答え」を技術で実現する**
2. データドリブンな営業組織への変革(個人の経験 → 組織のデータ)
3. 4営業所(大宮・川越・熊谷・越谷)の連携強化
4. ディーラー向けの提案品質向上(過去実績 + 未来予定の可視化)

### sys02さんの個人目標(プロジェクトを通じて獲得したいスキル)
- 爆速開発を**安定して複数回せる**状態(再現性ある型を持つ)
- 他者をプロジェクトに参加させられる状態(オンボード設計力)
- AIを使い倒す前提で、AIに振り回されない状態(理解と判断力)
- 思っていることをAIが正確に汲み取れる状態(言語化スキル)

コードを書けるようになることは目的ではない。**コードを書ける主体(AI)を使い倒す側の設計力・判断力・運用力**を磨くことが目的。

- **リリース判定**: 既存運用が完全に切り替わり、ブラウザで日次集計が見られる状態

### Phase 2: ディーラーダッシュボード(PartnerConnect)
- **期間**: 2026年6月〜8月初旬
- **目標リリース**: お盆前(8/8前後)
- **目的**: 副社長依頼のメイン機能。タブレットでディーラー訪問時に見せる
- **追加データ**: レンタカーシステムから車検・点検・新車・代替の予定データ
- **ユーザー**: MC営業担当(タブレット携行)、副社長
- **特徴**: 過去実績 + 未来予定の二本柱、新規店はエリア平均で対応

### Phase 3: 営業日報・入力系
- **期間**: 2026年9月〜
- **目的**: 営業活動の入力フローをアプリ化、Excel管理データを統合
- **機能**: テキスト日報、音声日報(Gemini)、訪問記録
- **R&D**: Phase 1〜2と並行して試作

### Phase 4: AIロープレ・MC全般アプリ化
- **期間**: 2027年〜
- **目的**: AI機能の本格導入、営業以外の業務も統合
- **機能**: ロープレ(Gemini Live API)、提案資料自動生成、各種社内業務

### Phase 5(将来構想): 基幹システム置き換え
- **期間**: 2028年以降
- **目的**: レンタカーシステム自体をMobickHubで代替
- **前提**: Phase 1〜4で十分な実績を積んでから慎重に検討

### グループ展開(将来構想)

## 5. 技術スタック(WHAT)

### 採用技術
| 領域 | 技術 |
|---|---|
| 言語 | TypeScript (strict mode) |
| フレームワーク | Next.js 15+ (App Router) |
| UIライブラリ | React 19+ |
| スタイリング | Tailwind CSS + shadcn/ui |
| グラフ | Recharts |
| テーブル | TanStack Table |
| データ取得 | TanStack Query |
| バックエンド・DB | Supabase (PostgreSQL + Auth + Storage + Edge Functions) |
| ホスティング | Vercel |
| コード管理 | GitHub (Privateリポジトリ) |
| AI(音声・大量処理) | Gemini API (Google AI Studio Tier 1以上) |
| AI(高品質文章) | Claude API |
| CSV処理 | papaparse |
| Excel処理 | SheetJS |
| バリデーション | Zod |
| フォーム | React Hook Form |

### 採用理由
- **Next.js + Supabase + Vercel** = フルスタック最小構成、インフラ管理ゼロ、sys02既経験
- **TypeScript** = 型安全性、AIとの相性が良い
- **shadcn/ui** = デザイン済み、カスタマイズ可、モックのコードベースとの整合
- **Pythonサーバ不要** = Next.js API Routesでバックエンド完結
- **Gemini AI Studio Tier 1** = 学習データ利用なし、業務利用OK、コスト最適

### 採用しないもの(明示的に)
- FastAPI / Pythonサーバ → Next.js API Routesで代替
- Vertex AI → AI Studio Tier 1で十分(エンタープライズ要件出てから検討)
- 既存Claude Skills連携 → MCにClaude未配布のため、Webアプリ独立で実装

## 8. 開発フロー(HOW)

### ブランチ戦略
- `main` — 本番。直push禁止(Branch Protection)、PR必須
- `feature/<機能名>` — 機能開発ブランチ。Issueと1対1で対応
- `fix/<内容>` — バグ修正ブランチ
- `chore/<内容>` — 雑務・設定変更

### PR運用
- 1 Issue = 1 PR = 1 機能 を原則
- PRテンプレートで「やったこと / 設計判断 / 学んだこと / 次回に活かせること」を記録
- Vercel Previewで動作確認後にマージ
- 重要PRは sys02 が動作確認、急ぎでない場合は1日寝かせて翌朝マージ判断

### マイグレーション管理
- スキーマ変更は必ず `supabase/migrations/` にSQLファイルを追加
- ローカル開発時は `supabase db push` で dev環境に反映
- 本番反映は明示的にPC前で `supabase db push --project-ref <prod>` で実行
- 直接Supabase管理画面でテーブル変更しない(マイグレーション履歴に残らないため)

### コーディング規約
- ファイル命名: ページ `app/[機能]/page.tsx`, API `app/api/[エンドポイント]/route.ts`, コンポーネント `components/[機能]/[Name].tsx`
- 命名: コンポーネントPascalCase、関数/変数camelCase、定数UPPER_SNAKE_CASE
- Supabaseテーブル: snake_case、IDはUUID、`created_at` `updated_at` `updated_by` を全テーブルに
- コミットメッセージ: 日本語OK、形式 `[Phase1] 日次集計テーブルのスキーマ追加`

### MCPの使い方
- **Supabase MCP** はdev環境を基本接続先とする
- 本番への変更は必ず Claude Code + マイグレーションファイル経由
- 危険操作(DROP TABLE等)は人間が必ず確認してから実行

### スマホ・移動中の開発
- アイデア整理・設計議論はClaude.aiで(MCP活用)
- GitHub Issue/PRのレビュー・コメントはモバイルで
- @claude メンションでクラウド側Claude Codeを起動するパターンも活用
- ローカル本格実装はPC前で集中

## 9. セキュリティ・事故防止

### 必ず守ること
- APIキーはコードに書かない。`process.env.<KEY>` で環境変数経由
- `.env.local` は絶対にGitHubに上げない(.gitignore で除外確認)
- 新しいテーブルを作ったら**必ずRLS(Row Level Security)を有効化**
- `NEXT_PUBLIC_` プレフィックスはブラウザに露出してOKなものだけ
- 本番DB操作は必ず明示的に。MCPで誤って本番を触らないよう接続先確認

### 役員データ・個人情報の扱い
- 担当者名・取引先名はMC社内データ。外部漏洩しないよう厳格管理
- ディーラー側の数字は「ディーラーごとに分離して見せる」設計(他社の数字が見えないように)
- ログイン認証は必須(Phase 1からSupabase Auth導入)
- 役員データへのアクセスログは保持(誰がいつ何を見たか追跡可能に)

### キー漏洩した場合
1. 即座に該当キーを無効化(各サービスの管理画面で revoke)
2. 新しいキーを発行して `.env.local` と Vercel に登録
3. コミット履歴から消すより、無効化を優先

### 役員コミット状態を踏まえた追加対策
- 本番環境への変更は必ず Vercel Preview での動作確認を経る
- リリース前には sys02 + 配信担当者 + 副社長 の三段階チェック
- 障害発生時の連絡フロー(誰に・どの順で・何を)を整備
- ロールバック手順を確立(直前バージョンへの即時復帰)

## 10. AIへの依頼スタイル(STANCE)

これは sys02 が「AIに振り回されない / 思っていることが正確に伝わる」状態を作るための、AI(Claude)への動作指示。

### 設計議論を依頼されたとき
- **いきなり実装に入らない**。まず方針を2〜3案出して比較する
- **トレードオフを必ず明示**(メリットだけでなくデメリットも)
- 「これでいいですか?」と聞く前に、判断材料を出す
- sys02 が選んだ案について、選ばなかった案のデメリットを軽く触れる

### コード実装を依頼されたとき
- 作業前に**変更ファイル一覧と実装ステップ**を提示し、sys02のOK後に着手
- 新しいパターン(初めて使うライブラリ・手法)が出てきたら、**何が新しいかを明示**
- 既知パターンの組み合わせなのか、新規学習領域なのかを分けて伝える
- コード生成後、「今回新しく出てきた概念」を1〜2行で要約

### 説明・解説のスタンス
- sys02 の慣れた言葉(Python、Excel、業務用語)で対比して説明する
- ソフトウェア工学の用語を使うときは初出時に簡単な説明を添える
- 「業務文脈と技術の橋渡し」を意識する(技術がsys02の業務でどう活きるか)

### 判断の区別
- AIが判断していい部分(慣習的・標準的な選択)と、sys02が判断すべき部分(業務固有・戦略的な選択)を区別して伝える
- sys02が判断すべき部分は「ここは判断してほしい」と明示する

### 質問の返し方
- 曖昧な依頼には実装に入らず、「○○の場合と△△の場合で答えが変わるけどどっち?」と聞き返す
- ただし、軽い雑談や明確な質問にはサクッと答える(過剰な確認はうるさい)

### コードレビューの依頼を受けたとき
- 重大度別(致命的/重要/軽微)で問題を列挙
- オブラートに包まない。率直に
- 「これは慣習として知っておくと良い」というコメントは別建てで

### 応答の冗長さ
- 重要な決定や設計議論では十分に説明する(理由を理解できるように)
- 単純な作業確認や雑な質問は短く返す
- sys02のスマホアプリでも読める長さを意識する

### MobickHub特有の文脈
- 役員コミット状態を踏まえ、「リスク」「タイムライン影響」「副社長への説明可能性」を意識した提案をする
- 「Phase 1で済ませるか、Phase 2に送るか」の判断を促す質問を適切なタイミングで投げる
- スライドのモック内容との整合を意識する(コードはGitHubで別途共有予定)

## 11. ドキュメント方針(LEGACY)

「未来のsys02」「将来参加するメンバー」が読んで理解できる状態を維持する。

### 必ず残すドキュメント
- **README.md** — プロジェクト概要、セットアップ手順、開発フロー
- **CLAUDE.md** — Claude Code向けのプロジェクト方針(このファイルと同期)
- **docs/decisions/** — ADR (Architecture Decision Record)。重要な設計判断を1判断1ファイルで記録
- **docs/onboarding.md** — 新規メンバー向けの環境構築・開発開始手順
- **docs/glossary.md** — ドメイン用語集
- **docs/data-model.md** — 主要テーブル定義と意味
- **supabase/migrations/** — DBマイグレーションファイル(時系列順)

### ADRの形式

```
# ADR-NNN: タイトル
## 決定日
## 文脈(背景・課題)
## 検討した選択肢(複数案)
## 決定
## 理由
## 影響(ポジティブ・ネガティブ両方)
```

### 想定する初期ADR
- ADR-001: プロジェクトキックオフと方針確定
- ADR-002: データモデルの設計方針(long format vs wide format)
- ADR-003: 認証方式(Supabase Auth + メールリンク? OAuth?)
- ADR-004: ディーラーカテゴリ・店舗のマスタ構造
- ADR-005: 営業所×担当者×ディーラーの権限設計

### PR説明の形式

```
## やったこと
## 設計判断(なぜこう実装したか)
## 詰まったところ・学んだこと
## 次回に活かせること
## 動作確認(Vercel PreviewのURL等)
```

## 14. リスクと対策

### リスク一覧

| リスク | 影響 | 対策 |
|---|---|---|
| レンタカーシステム担当者の協力が得られない | Phase 2着手不能 | 5月中にヒアリング開始、副社長経由で正式依頼も検討 |
| Phase 1の置き換えで配信担当者の業務が混乱 | 全社の信頼失墜 | β期間を設けて並行運用、切替日を明確に告知 |
| 役員ごとの期待値がバラバラ | リリース後に「思ってたのと違う」 | 月次デモで擦り合わせ、副社長経由で他役員にも共有 |
| タブレット手配が間に合わない | Phase 2リリースしても配れない | 6月中に機種選定・発注の意思決定を確定 |
| Vercel/Supabase の無料枠を超える | コスト発生・サービス停止 | 月次でコスト確認、有料プラン移行のトリガー設定 |
| sys02の業務逼迫で開発が止まる | 全体遅延 | 部内協力者を早期に巻き込む(ペアプロ・知識共有) |
| Excelの構造変更が起きる | 取り込み不能 | 配信担当者と密連携、変更時の即時アラート設計 |

### 監視すべきKPI
- 開発進捗: Phase毎の完了率(週次)
- 利用率: ログインユーザー数、画面別PV(Phase 1リリース後)
- データ品質: 取り込みエラー率、データ更新ラグ
- パフォーマンス: ページ表示速度、API応答時間
- コスト: Vercel・Supabase・AI API の月次費用
